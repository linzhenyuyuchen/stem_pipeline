# 模型与新增训练数据对比页面生成指南

本文档总结当前 MMMU-Pro 离线可视化的生成方案。下次获得新的模型结果、新增数据统计 HTML，并需要生成相同类型的模型对比、训练数据覆盖分析和总结性结论时，可按本文档操作。

## 1. 当前实现位置

- 页面生成脚本：`comparison_pangu_vs_qwen/build_midtrain_comparison.py`
- 生成后的离线页面：`comparison_pangu_vs_qwen/pangu_vs_qwen_sampling_offline.html`
- 评测标签：`portrait/labels.parquet`
- stage2 抽样映射：`comparison_pangu_vs_qwen/case_comparison.csv`
- stage2-caption / stage2-qa 历史聚合：`comparison_pangu_vs_qwen/comparison_data.json`

运行方式：

```bash
cd /home/ma-user/work/others/w00911759/evaluation_analysis
python comparison_pangu_vs_qwen/build_midtrain_comparison.py
```

生成脚本会直接覆盖同目录下的 `pangu_vs_qwen_sampling_offline.html`。页面包含全部数据和 JavaScript，不依赖服务器或网络，可直接用浏览器打开。

## 2. 页面当前提供的能力

页面由以下部分组成：

1. 92B/505B 与 Qwen 的总体准确率对比。
2. 模型选择、分析维度、最小样本量、显示行数选择。
3. domain、genre、knowledge_points 单维和交叉维度差异表。
4. stage2-caption、stage2-qa、mid-train 三列训练数据覆盖量。
5. 所选模型相对 Qwen 的弱项和 mid-train 上采样建议。
6. 92B-midtrain 与 92B-stage2-part3 在相同 1,500 个 case 上的严格配对比较。
7. 数据量与模型表现的关系分析。
8. mid-train 新增量与能力提升的关系分析。
9. “符合预期、部分符合预期、不符合预期、证据不足”四类上层结论及行动建议。

## 3. 输入文件要求

### 3.1 模型结果 JSON

模型结果文件需具有以下结构：

```json
{
  "result_details": [
    {
      "id": 0,
      "eval_result": true,
      "prediction": "...",
      "ref_answer": "..."
    }
  ]
}
```

实际计算只强制依赖：

- `result_details`
- 每条记录的 `eval_result`
- 建议保留唯一且稳定的 `id`

`eval_result` 会转成布尔值，准确率定义为 `eval_result=true` 的行数除以总行数。

### 3.2 labels.parquet

当前页面使用以下字段：

- `domain_top1`
- `domain_top1_name`
- `genre_top1`
- `genre_top1_name`
- `knowledge_points`

其中 domain 和 genre 使用 Top-1；knowledge_points 是多标签字段，一条 case 可以进入多个知识点分组。

### 3.3 新增训练数据 HTML

当前 mid-train HTML 内嵌一个 JSON 对象：

```javascript
const B={...};
```

生成脚本读取：

```text
B.agg.all.rows
B.agg.all.metadata.domain_label
B.agg.all.metadata.genre_label
B.agg.all.metadata.knowledge_points
```

每个 metadata 字段建议包含：

- `counts`
- `count_total`
- `rows_with_value`
- `occurrences`
- `truncated_to`，若只保留 Top-N

当前新增数据文件由脚本顶部的 `MIDTRAIN_HTML` 指定。

### 3.4 stage2-caption 和 stage2-qa

当前生成脚本从旧版 `comparison_data.json` 中读取已完成的聚合结果：

```text
training_distribution.cap
training_distribution.qa
```

对应源 HTML 为：

- stage2-caption：`cap_part1.html`、`cap_part2.html`、`cap_part3.html`
- stage2-qa：`qa_part1.html`、`qa_part2.html`

如果以后替换这些文件，不能只替换 HTML 文件名；还需要重新聚合新 HTML，或者修改 `training_data()` 直接解析各 HTML 中的 `const REPORTS={...}` 并汇总每个 dataset 的 metadata。

## 4. 最重要的数据对齐规则

### 4.1 全量结果与标签完全同序

如果新模型结果和 `labels.parquet` 行数相同，并确认顺序一致，可直接位置对齐：

```python
labels.iloc[i] <-> model_result_details[i] <-> qwen_result_details[i]
```

当前 92B、505B、Qwen 和 labels 都是 3,460 行，使用的就是这种方式。

不要仅凭“行数相同”推定顺序一致。生成前至少检查：

- 首、中、末若干条的 `id` 或题目是否一致；
- 若结果包含稳定 case key，应优先验证 case key；
- 是否存在跳行、过滤、重排或重复。

### 4.2 抽样结果或顺序不同

如果旧模型只评测了部分 case，不能把它与新模型的前 N 行直接比较。

必须准备映射表，例如当前的 `case_comparison.csv`：

```text
index,pangu_result_id,qwen_result_id,...
vision_0,0,0,...
vision_1,1,1,...
```

当前 stage2 对比使用：

```python
新模型记录 = new_result_details[qwen_result_id]
旧模型记录 = old_result_details[pangu_result_id]
```

这样才能在相同的 1,500 个 case 上计算 paired uplift。

如果下次没有现成映射表，应先基于稳定 case key、原始数据 index、图片 MD5 或题目 ID 建立映射，再生成可视化。

## 5. 接入新模型结果

编辑生成脚本顶部的 `MODEL_FILES`：

```python
MODEL_FILES = {
    "92B": Path("...result.json"),
    "505B": Path("...result.json"),
    "NEW_MODEL": Path("...new_model_result.json"),
}
```

然后完成以下检查：

1. 新结果是否包含 `result_details` 和 `eval_result`。
2. 新结果行数是否与 Qwen、labels 一致。
3. 新结果顺序是否与 labels 一致。
4. 页面 HTML 模板中的模型下拉框是否加入对应 option：

```html
<option value="NEW_MODEL">NEW_MODEL vs Qwen</option>
```

页面的数据计算会自动遍历 `MODEL_FILES`，但当前下拉框选项是显式写在 HTML 模板中的，因此新增模型时两处都要修改。

如果基准模型不再是 Qwen，还需修改：

- `QWEN` 路径；
- 页面标题与说明文字；
- `qwen_correct`、`qwen_accuracy` 等展示文案。内部变量可以不改名，但为避免误解，建议同步重命名。

## 6. 接入新的数据统计 HTML

### 6.1 用新 HTML 替换当前 mid-train

如果新 HTML 仍使用 `const B={...}` 和相同字段结构，只需修改：

```python
MIDTRAIN_HTML = ROOT / "stage2_data_html/new_overall.html"
```

重新运行生成脚本即可。

### 6.2 在现有三列之外增加第四列

需要同时修改四部分：

1. `training_data()`：解析新 HTML，并在返回值中增加一个 family。
2. HTML 表头：增加新数据列。
3. `render()` 和 `renderStage2Comparison()`：增加对应的 `cell()`。
4. `renderCoverage()`、`renderAnalysis()`：将新 family 纳入数据量合计或单独展示。

例如：

```python
return {
    "stage2_caption": caption,
    "stage2_qa": qa,
    "midtrain": mid,
    "next_stage": next_stage,
}
```

同时注意：如果“当前总训练量”应包含新数据，需要把 JavaScript 中的 family 列表由：

```javascript
['stage2_caption', 'stage2_qa', 'midtrain']
```

扩展为：

```javascript
['stage2_caption', 'stage2_qa', 'midtrain', 'next_stage']
```

## 7. 标签归一化规则

训练 HTML 和评测画像的标签格式并不完全相同，当前页面做了以下统一：

- 删除评测标签末尾的编码，例如 `[D10.03]`。
- 将显示分隔符 ` / ` 和源数据分隔符 `-` 统一。
- domain 统一到前两级，以匹配训练数据报告。
- genre 保留完整分类。
- knowledge_points 使用原始字符串精确匹配。

示例：

```text
数学 / 几何 / 平面几何 [D10.03.01]
```

会映射到：

```text
数学-几何
```

如果新数据使用不同的分类层级或命名方式，应先修改 Python/JavaScript 中的 `trainKey()` 归一化规则，否则页面会出现大量错误的 0 覆盖。

## 8. 页面核心指标口径

### 8.1 模型差异

```text
Δ(pp) = 所选模型准确率 - 基准模型准确率
```

- Δ > 0：所选模型领先。
- Δ < 0：所选模型落后。
- n：该标签在评测集中的 occurrence 数。

knowledge_points 是多标签展开统计，所以不同知识点的 n 之和可以超过 case 总数。

### 8.2 训练数据量

页面显示：

```text
标签 occurrence（标签 occurrence / count_total）
```

这不是去重样本数。一条多标签数据可能贡献多个 occurrence。

### 8.3 严格配对提升

```text
uplift(pp) = 新模型在配对子集上的准确率 - 旧模型在相同配对子集上的准确率
```

只有两模型使用完全相同的 case 时，该指标才可解释为版本提升。

## 9. 自动结论的生成规则

当前结论固定分析 92B-midtrain。

### 9.1 数据多且对 Qwen 表现好/不好

1. 当前总训练量 = stage2-caption + stage2-qa + mid-train。
2. 仅在训练量大于 0 的有效评测标签中计算分位数。
3. 训练量位于该维度前 25% 的标签定义为“数据量多”。
4. 92B − Qwen ≥ 0：数据多且表现不弱于 Qwen。
5. 92B − Qwen < 0：数据多但表现仍不理想。

样本量门槛：

- domain：n ≥ 10
- genre：n ≥ 10
- knowledge_points：n ≥ 3

### 9.2 mid-train 是否获得符合预期的提升

1. 在严格配对子集上计算新旧 92B 的 uplift。
2. mid-train 数据量位于该维度正数标签的前 25%，定义为“新增量大”。
3. uplift > 0：符合预期。
4. uplift ≤ 0：提升较少、没有提升或退化。

“符合预期”只说明新增量和版本提升方向一致，不表示已经追平 Qwen。页面会同时保留“相对旧模型提升”和“相对 Qwen 差距”，用于区分：

- 已提升且已追平；
- 已提升但仍未追平；
- 数据很多但没有提升。

## 10. 如何形成上层结论

不要只罗列单个标签，应把结果归纳为以下四类：

### A. 符合预期

特征：新增数据量大、paired uplift 为正、对基准模型差距缩小或已经追平。

建议：保持投入，重点增加难度、表达方式和视觉风格的多样性，避免同质重复。

### B. 部分符合预期

特征：paired uplift 明显为正，但当前模型仍落后基准模型。

建议：基础覆盖已经有效，下一阶段应补复杂组合、多步推理、跨图关联、困难负例，而不是只扩大原有简单数据。

### C. 不符合预期或出现饱和

特征：新增量大，但 paired uplift 接近 0 或为负。

建议：暂停等比例扩量，优先检查：

- 重复率和近重复；
- 训练/评测答案噪声；
- 简单题占比过高；
- 数据格式与真实评测形态不匹配；
- 训练目标是否真正要求模型执行相关推理。

然后基于失败案例补充小规模、高质量、可验证的数据。

### D. 证据不足

特征：Δ 或 uplift 很大，但评测 n 很小；或知识点未进入训练 HTML 的 Top-N。

建议：先扩大独立评测集，不要直接据此大规模调整训练数据。采样优先级可使用：

```text
优先级 ≈ 错误幅度 × 可信样本量 × 数据缺口
```

避免只根据小样本的 ±50 pp、±100 pp 极值做决策。

## 11. 上采样建议口径

当前页面仅将上采样权重作为方向性建议：

```text
评测严重度 = n × max(-Δpp, 0) / 100
```

权重综合：

- 70%：相对基准模型的超额错误严重度；
- 30%：mid-train 相对 stage2 的覆盖稀缺度；
- 映射范围：1–4×。

该权重适合用于确定数据桶优先级，不建议直接将多个维度的权重相乘。更稳妥的方法是按 domain、genre、knowledge_points 分别建桶并轮换采样。

1. 模型切换后总体卡片和明细表是否同时变化。
2. domain、genre、knowledge_points 是否都有数据。
3. 单维和双维交叉模式是否能切换。

## 13. 推荐的完整操作清单

每次生成新页面时按以下顺序执行：

1. 收集新模型、基准模型、旧模型结果 JSON。
2. 确认 `eval_result` 字段和结果行数。
3. 验证新模型、基准模型与 labels 的顺序。
4. 若存在抽样模型，生成或验证 case 映射 CSV。
5. 检查新增训练 HTML 中的 JavaScript 常量名和 metadata 结构。
6. 修改脚本顶部文件路径和模型名称。
7. 如新增数据列，同步修改训练 family、表头、渲染和结论合计。
8. 运行生成脚本。
9. 执行 Python 与 JavaScript 语法检查。
10. 检查总体准确率、paired uplift、训练总量和典型标签。
11. 浏览器检查筛选、排序、模型切换和交叉维度。
12. 最终结论按“符合预期、部分符合、不符合预期、证据不足”组织，并给出对应行动。

## 14. 当前方案的限制

- stage2-caption/qa 目前依赖旧版 `comparison_data.json`，尚未在新脚本中直接重新解析五个超大 HTML。
- 模型下拉框仍需手工增加 option。
- domain 的训练量只有前两级，无法精确区分更细的评测叶子标签。
- 训练报告只包含边际标签量，双维交叉表展示的是两条边际，不是联合样本数。
- knowledge_points 的 Top-N 报告会低估长尾覆盖。
- 当前分析是相关性分析；数据量和性能同时上升不等于严格因果关系。

如果后续经常增加模型或数据版本，建议下一步把脚本改为配置驱动：通过一个 JSON/YAML 文件声明模型、基准、训练数据 family、HTML 解析方式和 paired mapping，使新增版本无需编辑 HTML 模板代码。
